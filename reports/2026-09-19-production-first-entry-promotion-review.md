## Findings

1. **P1: final vetting can discover a confirmed OUT player, yet the promotion output retains every affected lineup.** `promote_first.py:180–210` excludes such rows only from first-place eligibility; lines 225 onward still write all rows. In a scratch copy of the actual book, injecting a new `report:Out` flag and weight 100 for Javonte Williams into the final full-vetter result, with consistent per-row risk/hard/material fields, succeeds and outputs **all 28 affected rows**. The fresh-vetter OUT is absent from old replacement flags, so even `guards_forcing_ineligible` is empty. This is a simulated boundary, not a statement that Williams is OUT. Refuse publication and request a fresh replacement pass when either final vetting or the replacement flags establish a true OUT-class designation or gated QB in any delivered row. Do not conflate vanished-market/placeholder HARD classifications with confirmed unavailability. An old rollback book with the same newly OUT player is not a valid fallback.

2. **P1: the runner publishes its discoverable upload filename before its permutation check.** `run_promotion.sh:39` writes `upload-<tag>-promoted-paid-vetted-all.csv`; lines 42–58 validate it afterward. A failed emit or verification can leave that newest file in place. The runner's own comments and production handoff say the page discovers the newest matching filename. A failed check therefore does not reliably prevent discovery. Emit into private staging, verify against the chain upload and record the verified identities, then atomically publish the final filename (and associated sheet/manifest). On failure, no new upload candidate should be discoverable. This finding is source inspection; the actual host page was not executed here.

3. **P2: bank and candidate identities are recorded, not verified against the source run.** `load_banks()` checks shape/dtype, but the consumer never reads `RUN_DIR/receipt.json` or checks `replace.json.input_sha256`. Adding 1.0 to every player draw in one copied bank keeps its shape/dtype and is accepted; the reported head mean becomes **148.0388748779297**, while original receipts remain unchanged. Deleting the source run receipt also succeeds in the standalone consumer (the shell runner checks presence). Require source receipt byte equality with the replacement input receipt, and verify source frame/candidates/banks against the replacement input hashes and the bank sidecars' SHA256/size/shape/dtype. Do this before ranking, not only in the output receipt.

4. **P2: the new consumer reads all frame/candidate parquet columns.** `load_banks`, `candidate_orders`, and `check_packet` omit column lists. The current frame schema includes `actual`; candidate files may carry audit columns. None is needed for promotion. Restrict the consumer to `id, dk_player_id, salary, name` and candidates `players`. The runner also invokes a vetter that reads all frame columns: use a restricted reader or narrowly reviewed allowlist change for that invocation. The review intercepted every such read and decoded only its explicit input allowlist; no current-week outcome values were read.

Additional low-cost consistency fixes: reject `publishable != true` or active rehearsal flags from the replacement receipt directly, as well as the shell marker check; verify the approved rule hash; bind declared required K to book length and require positive integral contest entry counts. The standalone consumer currently accepts a receipt set to `publishable:false` with `no_fresh_dk:true`. This test intentionally omits the marker and is not evidence that the normal marked rehearsal bypasses the shell's existing marker check.
