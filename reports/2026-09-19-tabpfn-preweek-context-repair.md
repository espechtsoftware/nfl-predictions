# TabPFN upcoming context: enforce the target-week boundary before reading labels

The salary-week repair restores 2026 training rows. A support-only preflight found 863 labeled Week 1 rows and 43 labeled Week 2 rows in `nfl_features_salaryfix.player_week_training`; the control has no 2026 rows. The existing upcoming generator selects every nonnull training label. Thus a Week 2 refresh after the salary repair would include same-week context, contrary to the project's strict prior-week rule. No values from those 43 labels were opened.

Branch `fix/2026-09-tabpfn-preweek-context`, based on salary repair `9f218bab`, adds the season/week cutoff to the actual training SELECT before downloading any rows. Week 2 includes previous seasons and Week 1; Week 1 includes only previous seasons. Both full-plus-upcoming and upcoming-only refreshes share this query. With no upcoming target, the historical-only query remains identical. The receipt names the strict prior-season/week context and records its exclusive target. Invalid target formats and weeks fail before row access.

Validation: **14 targeted tests pass** across the new pre-week tests, upcoming-only contract tests and canonical PIT-cache tests. New tests execute the real top-level generator until its first query, then execute that exact query against a boundary fixture containing prior-season, prior-week, same-week and future rows. They verify the exclusion in both modes and preserve the no-upcoming query. The scratch adapter independently uses the same predicate and its two actual BigQuery dry-runs passed (76.7/77.2 MB estimated). That adapter is a separate controlled experiment with sorted input order; it is not the deployed source patch.

The actual currently deployed image's generator was independently extracted and SHA-verified to match the pre-fix source (`0d8a355b270e2ef5f6097bef51ca5d3ff1715e20951b4c2762b5594a5b9c9a81`). Therefore this is an activated production boundary, not a stale checkout concern. The patch is prepared for independent review; no live job/image/table change has been made. A release needs the reviewed generator image or a separately reviewed, pinned invocation, then a refresh before the lineup build. The ongoing isolated cache rehearsal writes only its scratch datasets.

Independent workstation review `ddd2e52` found no source defect. Its optional-component observation applies when `TABPFN_COMPONENTS=1` and `TABPFN_SEASONS` explicitly includes the target season: that path shares the filtered panel, so target-week component outputs are excluded too. The normal full-cache season list ends at 2025, so the Week 2 2026 live refresh does not lose historical-season targets. This scope is documented; the original exact-query boundary tests already exercise which target-week rows can enter that shared panel. No training-source rows are deleted.
